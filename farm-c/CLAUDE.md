# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`farm-c` is a standalone, pure-C port of the Python farm-economy simulator in
the parent directory. The repo-root `../CLAUDE.md` describes that Python
simulator (the domain model, the daily order, the balance workflow) and still
applies here — this file covers only what is specific to the C port.

**Python is the oracle, not a rough guide.** The target is the
bit-compatible column of `../docs/c-port-plan.md` Section 7: same seeds, same
RNG stream, same floating-point operations, same rounding, same trajectory.
"Same rules, similar results" is not the bar. Every ported function matches
its Python source function-for-function including tie-break order and
rounding, and every layer is verified against recorded output from the real
Python modules (`tests/fixtures/*.json`, generated by `../tools/export_*_fixtures.py`).

The port was built in phases; `README.md` documents each one and the current
scope boundary. Deliberately **out of scope**: the legacy `world=None`
`run_day` path (and its `water_farm`/`sell_all` actions), `summary.json` /
`summary_report.md`, and any process pool — `farm-c batch` is sequential.

## Commands

All from `farm-c/`.

```bash
make test              # build + run all 9 test binaries under ASan+UBSan, then tests/test_cli.sh
make farm-c            # build the CLI (also ASan+UBSan)
make profile           # build/farm-c-profile: -O2, NO sanitizers -- the only build to time
make clean

# One test binary at a time (each is a plain executable, no test runner)
make tests/test_engine && ./tests/test_engine
./tests/test_agents    # prints "N checks, M failed"

# Regenerate fixtures from the real Python modules (needs the repo's venv)
make fixtures            # agents.json    <- ../agents/*.py decision surface
make fixtures-rng        # rng.json       <- CPython random.Random
make fixtures-physics    # physics.json   <- crop_growth.py + weather.py
make fixtures-mutation   # mutation.json  <- actions/inventory/markets/processing/contracts

# `make test` alone needs no Python -- it re-runs against the checked-in fixtures.

# Run the simulator
./farm-c single --strategy profit_optimizer --seed 42 --verbose
./farm-c batch --runs 1000 --seed 42 --csv reports/run_results.csv --html reports/dashboard.html
./farm-c batch --runs 100 --days 30 --start-money 300     # diagnostic overrides
```

Default config directory is `../config` (the same JSON the Python simulator
reads — there is no separate C copy). Default strategy is `profit_optimizer`.
An omitted seed is generated and printed (`actual_seed` / `base_seed`).

**Never time or memory-profile the default build.** `farm-c` and every
`tests/test_*` binary carry `-fsanitize=address,undefined`, which inflates CPU
time ~2-3x and distorts peak memory. Use `build/farm-c-profile` for
Instruments / `sample` / `/usr/bin/time -l`. (ASan's leak detection on the
regular build is still fine and worth keeping in the loop.)

## Bit-exactness invariants

These are load-bearing. Breaking any of them produces silent 1-ulp drift that
only the fixture suites catch:

- **`-ffp-contract=off` on every compile and link rule.** Without it a
  compiler may fuse `a + (b - a) * x` (`rng_uniform`, `economy_rules.c`) into
  one rounded FMA where Python does two roundings. This already caught
  `rng_uniform`/`rng_roll_price` drifting in ~2% of `test_rng.c`'s cases. Any
  new build rule must carry `$(FP)`. Same requirement as
  `../simulation/_fastplotmodule.c`.
- **`py_min`/`py_max`/`clamp01`/`py_neumaier_sum`/`py_round_ndigits`
  (`include/pyfloat.h`).** Use these, never `fmin`/`fmax`, a comparison chain,
  plain accumulation, or a hand-rolled round. They reproduce CPython's exact
  bytecode semantics (ties and signed zero keep the first argument; `sum()`
  has been Neumaier-compensated since 3.12).
- **Ties keep the first element.** Python's `min`/`max`/`sorted` are stable,
  so every C loop here replaces its running best only on a *strict*
  inequality, and every sort is stable or explicitly decorated.
- **RNG draw order and count.** `src/rng.c` is a bit-exact MT19937 port of
  `random.Random`. Adding, removing, or reordering a draw relative to the
  Python source changes every recorded seed's outcome. `rng_randrange_2_32`
  is the one call that draws `getrandbits(33)` (the batch seed-minting path);
  everything else uses the `k<=32` fast path.
- **`AGENT_REGISTRY` order (`src/agent_registry.c`) mirrors `../main.py`'s
  dict order.** Reordering it silently changes which minted seed lands on
  which strategy for a default (no `--strategy`) batch.
- **The 23 numbered steps in `src/engine.c:engine_run_day_observed`** are the
  Python `run_day` order. Changing it is a breaking change for every recorded
  seed, exactly as `../CLAUDE.md` says for the Python engine.
- **Contract forecasting stays timeline-aware.** `contracts.c`'s
  `_item_capacity` equivalent tracks arrival days, slot free-days, recipe
  duration and deadlines; the "future inputs / recipe quantity" shortcut
  changes which contracts agents accept (`../docs/c-port-plan.md` Section 8).

Cross-language spot checks are cheap and worth doing after engine-level
changes: a `--seed` shared between `./farm-c batch` and
`python3 ../main.py batch` mints the identical per-run seed for the identical
strategy at the identical position, so the two are diffable run-for-run.

## Architecture

**Layering** (each layer verified against Python before the next was built):
`rng.c` → `crop_growth.c`/`weather.c` (physics) → `actions.c`/`inventory.c`/
`markets.c`/`processing.c`/`contracts.c` (state mutators) → `config_loader.c`
→ `engine.c` (daily loop) → `runner.c` (single run) → `batch.c` →
`aggregate.c`/`warnings.c`/`dashboard.c` (reporting).

**Agents are a vtable, not a class hierarchy.** `Agent` and `AgentVTable` are
the same type (`include/agent.h`); all 11 agents are stateless singletons, so
the table *is* the instance. Agents take `const FarmState *` and write
decisions into caller-owned buffers — they never mutate state, exactly as in
the Python port. Control agents that subclass `ProfitOptimizer` in Python copy
its function pointers field-for-field and override only what they mean to;
`tests/test_agents.c` asserts those pointers are still `==`, the C analogue of
Python's `NeglectfulGrower.choose_crop is ProfitOptimizer.choose_crop`.

**Ownership** (`../docs/c-port-plan.md` Section 9): `ResolvedConfig` owns all
config strings/arrays; `FarmState` references it and never frees it;
`runner_run_single` owns the `FarmState` in its `RunResult`. Every
`*_destroy` is safe on a zeroed or partially-initialized object and must be
called exactly once, including after a failed load or run. Prefer indexes over
pointers into vectors that may `realloc`. Vector growth is centralized in
`vec_util.c` (`vec_grow` for one-more-element, `scratch_buffer_reserve` for
reusable per-call scratch arrays whose pointer is invalidated by the next
growth on the same buffer).

**Config is dense and indexed.** `ResolvedConfig` is immutable after load;
state arrays are indexed directly by `ItemId`/`UpgradeId`/etc. rather than
hashed. `derived.c` recomputes what Python memoizes — a static config needs no
cache.

**One source of truth for derived numbers.** The terminal summary table, the
balance warnings, and the HTML dashboard all read `aggregate.c`; no consumer
recomputes an average. `--html` is fed from the batch callback (not from the
CSV, which drops the crop-count fields the charts need), so it renders the
batch you are running, not an archived one; the CSV stays the exact per-run
record (`%.17g` vs the page's display-only `%.10g`).

## Tests

Nine binaries plus `tests/test_cli.sh`, all driven by `make test`. Each
fixture-driven suite (`test_agents`, `test_rng`, `test_physics`,
`test_mutation`) replays recorded Python output and asserts `==`, never an
epsilon — floats are exchanged as `float.hex()` strings, so a fixture loader
must `strtod(valuestring)`, not read cJSON's `valuedouble`. `test_mutation`
compares a *full snapshot* of every mutable state field before and after each
call, not just the function's documented return, which is what catches an
incidental extra mutation.

There is **no golden-replay baseline for the C engine** yet (contrast
`../.claude/skills/replay-guard`, which guards the Python `simulation/`
package). `test_engine.c` covers step ordering, bookkeeping, failure cleanup,
and same-seed repeatability. Whole-trajectory confidence comes instead from
`../.claude/skills/c-parity`, which runs the same minted seeds through both
implementations and diffs every run bit-for-bit against raw `PlayerState`
values:

```bash
python3 ../.claude/skills/c-parity/scripts/c_parity.py check
```

Run it before and after touching anything under `src/` or `include/`, and
after any change to `../simulation/`, `../agents/`, or `../config/` — the port
is a mirror, so moving the reference moves what the mirror must match. It
passes on a clean tree (verified to 2200 runs), so any failure is yours to
explain before the change is done.

When changing a ported function, regenerate the matching fixture set only if
the *Python* changed. If the fixture and the C disagree and Python did not
change, the C is wrong.

## Build mechanics

Objects and `.d` header-dependency files go to `build/`, mirroring `src/`'s
layout — **never build in tree**. `-MMD -MP` is what makes editing a header
(including `src/dashboard_js.h`, which carries the whole dashboard renderer)
actually rebuild dependents; without it stale `.o` files link silently.
`src/cJSON.c` + `include/cJSON.h` are the production vendored parser;
`tests/third_party/cJSON.*` is a legacy copy used only by the older fixture
loaders.
